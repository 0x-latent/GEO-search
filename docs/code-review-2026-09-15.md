## P1：优先处理

### 1. 自动调查基线选择绕过用户数据隔离

位置：[investigation_store.py:794](D:/项目/prod/geo-search/backend/app/services/investigation_store.py:794)、[investigation_routes.py:73](D:/项目/prod/geo-search/backend/app/api/investigation_routes.py:73)。

**触发条件：** 两个用户拥有同产品、同问题集指纹的不同批次；用户创建调查时不显式传入基线。

`select_baseline()` 仅按产品、问题集和日期寻找上一批次，没有 owner 或可见数据集限制。API 只检查显式提交的基线，调查详情又只检查当前数据集权限。调查工具随后直接读取选出的基线回答与信源。

**复现结果：** Alice 的当前批次自动选中了 Bob 的历史批次；`diff_answers()` 返回了 Bob 的私有回答标记，Alice 同时可以读取该调查详情。自动扫描也调用同一基线选择函数。

**建议：** 将允许访问的数据集集合传入基线选择，选出后再次检查权限；详情与证据访问同时检查当前批次和基线批次。后台自动扫描按数据集归属执行相同限制。

### 2. 自助任务的问题 ID 可使采集结果写出任务目录

位置：[03_query_models.py:217](D:/项目/prod/geo-search/scripts/03_query_models.py:217)、[job_routes.py:124](D:/项目/prod/geo-search/backend/app/api/job_routes.py:124)。

**触发条件：** 已登录用户直接提交 `/api/jobs`，在 `questions[].id` 中放入相对路径或绝对路径；相应模型调用返回结果。

任务入口接受任意问题字典，不强制经过上传解析器，也没有校验 ID。采集脚本将 ID 拼成文件名后直接写入，没有检查解析后的路径是否仍在当前模型目录内。

**复现结果：** `id='../../escaped'` 被任务创建逻辑接受，模拟采集成功后生成了 `job/escaped_r1_nosearch.json`，越过了 `job/raw/qwen` 和 `job/raw` 边界。

**影响：** 可在进程权限范围内向已有目录写入或覆盖符合结果文件命名后缀的 JSON 文件，破坏任务间文件隔离。这里没有把问题扩大描述为任意代码执行。

**建议：** 使用服务端生成的安全 ID，约束问题结构和 ID 唯一性；写文件前解析绝对路径并检查其必须属于当前模型目录。

### 3. 旧版用户配置兼容路径可跨用户读取和删除

位置：[user_config_store.py:30](D:/项目/prod/geo-search/backend/app/services/user_config_store.py:30)、[user_config_store.py:104](D:/项目/prod/geo-search/backend/app/services/user_config_store.py:104)。

**触发条件：** 部署保留旧版用户配置目录，另一个门户用户名经过旧规则清洗后与原用户名相同。

新写入采用哈希目录，但读取回退及重置仍使用删除特殊字符后的旧目录名。用户名 `a.b` 与 `ab` 都会回退到 `ab`；重置操作还会删除该路径的文件。

**复现结果：** 在旧目录 `ab/knowledge_base.json` 放入私有配置，`load_effective_kb('a.b')` 成功读取；`reset_user_kb('a.b')` 删除了同一个文件。品牌配置存在相同逻辑。

**建议：** 使用可验证的旧用户归属映射做一次性迁移。无法证明归属时不自动回退或删除旧目录。

### 4. 仓库提供的 Nginx 配置阻断外部邀请投稿

位置：[nginx_geo_location.conf:1](D:/项目/prod/geo-search/scripts/nginx_geo_location.conf:1)、[ContributorReviewPanel.vue:49](D:/项目/prod/geo-search/frontend/src/components/source/ContributorReviewPanel.vue:49)。

**触发条件：** 按仓库部署脚本应用 `/geo/` 配置，外部投稿人没有门户会话。

前端生成同站点 `/geo/article-submit.html#invite=...&token=...` 邀请链接，而 Nginx 对整个 `/geo/` 执行门户鉴权并将未登录请求转到登录页。后端虽然将投稿页、投稿接口与资源列为公开路径，但请求首先被网关拦下。URL fragment 中的邀请令牌也不会发送给网关。

**验证方式：** 静态核对邀请链接生成逻辑、后端公开路径和部署脚本使用的 Nginx 模板；未连接线上服务器，因此不声称生产环境当前一定采用此完整配置。

**建议：** 为投稿入口、所需静态资源及 `/geo/api/contributor/` 设置明确的网关例外，由投稿会话机制负责鉴权；保留管理员和其他业务接口的门户鉴权。

## P2：数据与运行可靠性

### 5. 并发修订可能覆盖已接受版本的文件

位置：[contributor_store.py:380](D:/项目/prod/geo-search/backend/app/services/contributor_store.py:380)。

**触发条件：** 两个修订请求在多个 Web 进程或实例中重叠执行，且使用相同文件名。默认单 Web 进程的同步段执行会降低这一触发概率。

代码在事务外读取 `current_version + 1` 并写入固定版本路径，进入事务后没有重新校验版本及状态。第二个请求即使因版本唯一约束失败，之前写入文件的副作用也不会回滚。

**复现结果：** 在读版本和写文件之间插入另一请求：一个修订成功，另一个返回 `IntegrityError`，但数据库保存的文件哈希已与磁盘实际内容不符。Worker 可能审查并非成功提交的正文。

**建议：** 原子分配版本并复核状态；每次上传先写独立临时文件，只有成功取得版本的请求才发布正式文件，失败请求不得覆盖已有版本。

### 6. 旧审稿执行可以覆盖取消后的新重试

位置：[article_review_service.py:398](D:/项目/prod/geo-search/backend/app/services/article_review_service.py:398)、[article_review_service.py:354](D:/项目/prod/geo-search/backend/app/services/article_review_service.py:354)。

取消只修改数据库状态，原来的模型请求继续运行。重试复用同一个 job ID。旧执行抛异常时无条件把 job 和投稿改为失败；成功分支也仅检查状态是 `running`，不能区分是否已经属于新的执行轮次。

**复现结果：** 旧执行等待模型返回时取消并重试，新执行成功领取任务；随后旧执行超时，将新任务改为 `failed`，错误内容来自旧执行。

**建议：** 每次领取生成或递增执行标识。成功、失败、解析失败、知识库缺失等所有写入都应校验执行标识、租约归属、当前版本及状态；被取消或失去租约的执行只丢弃结果。

### 7. 已进入追踪的投稿修改发布信息后，追踪表仍使用旧链接

位置：[contributor_store.py:412](D:/项目/prod/geo-search/backend/app/services/contributor_store.py:412)。

`update_publication()` 更新投稿表，但仅在 `approved_waiting_publication` 状态时创建追踪记录；已经是 `tracked` 的投稿不会同步 `article_publications` 中的 URL、平台或发布时间。

**复现结果：** 审核通过后将发布链接从 `/old` 改成 `/new`，投稿详情返回 `/new`，正式追踪表仍为 `/old`。引用匹配继续针对旧地址，新链接产生的引用会漏计。

**建议：** 在同一事务中更新关联发布记录及匹配键，并刷新相关引用匹配；或者明确禁止修改已追踪记录，提供独立的发布记录变更流程。

### 8. 分析关键阶段失败后，整个任务仍可显示成功

位置：[job_store.py:32](D:/项目/prod/geo-search/backend/app/services/job_store.py:32)、[job_store.py:400](D:/项目/prod/geo-search/backend/app/services/job_store.py:400)。

`analyze`、`extract`、`verify` 全部被标记为非关键阶段。失败仅写日志，只要入库和物化进程返回零，最终状态就是 `success` 且 `error=None`；成功状态又不允许从重试接口继续补齐。

**复现结果：** 模拟上述三个阶段均返回 1、入库和物化返回 0，最终任务仍为 `success`。这是对状态机的复现，不代表所有真实失败都会让后续入库成功。

采集脚本也只打印成功/失败数量，没有把失败数量转成非零退出码；因此仅依赖进程退出码不足以判断结果完整性。

**建议：** 保存各阶段状态与产物完整性；允许部分结果保留，但应展示“部分失败/需重试”并支持补跑，而不是完整成功。

### 9. 推荐抽取失败被缓存为成功空结果，重试不会恢复

位置：[05_extract_recommendations.py:172](D:/项目/prod/geo-search/scripts/05_extract_recommendations.py:172)。

两次模型调用失败后，代码把 `recs` 设为 `[]`，随后照常写入 `log['completed']`。下一次执行命中缓存后直接跳过，无法区分“确实没有推荐”和“抽取失败”。

**复现结果：** 首次模拟两次异常，恢复模型后再次抽取同一回答：新增模型调用次数为 0，返回仍是空数组，跳过计数增加。由此可能漏记推荐和负面信息。

**建议：** 成功空数组与失败状态分开记录；失败键不能进入成功断点集合，后续重跑应重新调用。

### 10. 连续限流耗尽循环时，采集任务既无结果也无失败记录

位置：[03_query_models.py:255](D:/项目/prod/geo-search/scripts/03_query_models.py:255)。

限流分支注释称“不计入重试次数”，实际却在有限的 `for attempt` 循环中直接 `continue`。连续触发 429 时最终跳出循环，绕过普通失败分支，不记录失败、不增加完成计数，也不抛出异常。

**复现结果：** 将重试次数设为 2、两次均模拟 429，函数正常返回，执行日志条数为 0，完成计数为 0。上层仍可能继续分析不完整数据。

**建议：** 分离限流等待与普通重试计数，并设置总等待或总尝试上限；达到上限时必须落失败记录，让任务完整性检查能够发现缺失。

## 修复结果

- #1：自动基线限定为当前数据集同一用户；普通用户的列表、详情及操作同时检查当前批次和基线权限。
- #2：任务 API 和采集脚本共享问题 ID/正文/唯一性校验，落盘前检查解析后的文件路径边界。
- #3：取消旧用户名目录的自动读取与删除，保留原文件供核实归属后迁移；哈希目录的读写和重置保持可用。
- #4：为投稿页、投稿 API 和资源添加网关例外；补充上传大小配置，并验证部署配置替换可重复执行。
- #5：在写事务内检查投稿状态、分配版本，每次文件写入采用独立路径。
- #6：Worker 领取结果携带执行次数和归属标识；写入前校验状态、租约、执行次数和投稿版本，旧执行不能覆盖重试结果。
- #7：更新投稿发布信息时同步对应发布记录及匹配键，并清除该发布记录的旧引用匹配；不修改同一文章的其他发布渠道。
- #8：任一流水线阶段执行失败即标记任务失败并停止后续阶段；采集、抽取和准确率脚本将模型执行失败反馈给流水线。
- #9：失败抽取不写入成功缓存；旧版无法区分失败的空缓存会重新核验，版本 2 的成功空结果仍可复用。
- #10：限流受总尝试次数约束，耗尽后记录失败；采集结束核对预期结果数量，失败后可补采。

二次复查补充修复：

- 限流降低或恢复并发时保留原等待队列，避免已排队请求永久挂起；重叠的限流等待不会提前解除暂停，取消请求会归还并发额度。
- 投稿 Cookie 路径随网关转换为 `/geo/api/contributor`，使浏览器在子路径部署下能保持会话并正常退出。

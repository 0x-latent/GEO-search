# GEO 项目协作首版实施记录

基线：用户调整的 `业务流程图.posf`。分支：`codex/geo-agency-workflow`。
状态：本地实现与回归验证；尚未部署，未进行真实 KB 服务、模型或外部发布渠道联调。

## 已实现

- 新增“项目协作”入口：项目 Brief、产品范围、合作代理、渠道、目标问题、知识库编号映射、按序审批人、投稿截止与监测计划。
- 项目邀请沿用现有临时链接机制，绑定项目和公司。名单、详情、修订、原稿下载和发布回填均按项目隔离。同公司另一项目的邀请也不能访问本项目稿件。额度仅限制新投稿，用尽后仍可返回修改和回填。
- 项目稿件调用独立 KB 固定判据 API：用 GEO 自己的应用凭据、显式 agency 角色；校验产品、正文摘要、判据摘要、时间与结构；保留本次完整快照及历史报告。KB 未配置、不可用、产品缺失或超出正文长度上限时停止核验，不回退到本地旧知识库。
- Agent 根据知识及项目要求输出核验报告；固定禁用表达命中作为确定性阻断问题保留。所有稿件仍由指定人员审批；阻断问题须退修，或由当前审批人逐项记录误报依据后才能通过。
- 逐级审批绑定稿件版本与节点序号。只有当前指定审批人能操作，管理员不能通过旧入口越级批准项目稿件。重复点击、并发审批、旧页面请求只允许当前有效决定生效。
- 修订创建新版本并重新核验，清除旧版批准；所有审批历史保留。获批后正文变化也必须重审。
- “可发布”之后代理才能回填发布渠道、链接、实际时间和凭证说明，随后进入“待发布验收”。负责人填写核对依据，选择验收通过、发布信息补正或正文重审。验收绑定版本及发布记录修订号，不能把旧页面的结论用于新链接。
- 验收通过后登记文章并进入引用追踪；验收与登记之间若中断，Worker 可恢复登记。
- 定期按项目计划分析负责人已导入的相关产品 GEO 样本，保存观测历史、引用依据、引用文章数、模型分布和覆盖问题；过滤其他用户、其他产品及早于发布的引用。无样本明确显示为无样本。
- 项目复盘记录与归档。存在未完成稿件时不允许归档；归档后停止流转和周期监测，保留历史。

## 首版操作路径

1. 管理员在原有“信源分析 → 投稿审核”中创建代理公司。
2. 项目负责人进入“项目协作”，创建项目。审批人填写已有门户账户的准确用户名；可以设置“专家 → 负责人终审”等串行节点。
3. 在项目的“代理邀请”中生成临时入口，并交给对应合作代理。
4. 代理进入项目上传稿件，等待 Agent 核验；审批人到“项目协作 → 稿件与审批”查看当前稿件、核验报告和依据历史。
5. 完成所有必需审批节点后，代理下载当前获批版本并发布，回填发布资料。
6. 项目负责人打开发布页，人工核对正文与批准版本，记录验收结论。
7. 在“我的分析”按计划采集并导入 GEO 批次；“监测与复盘”定期或手动更新观测，最后复盘归档。

## 环境与兼容

Web 和审稿 Worker 均通过部署环境传入：

```text
GEO_KB_URL=https://<知识库服务地址>
GEO_KB_KEY=<为 geo 应用配置的服务端凭据>
```

`GEO_KB_URL` 填服务根地址，不包含 `/api/v1`。KB 服务需为 `geo` 调用方提供获准的 agency 判据读取能力；不复用 KOL 的密钥。配置值未填写不会影响旧投稿流程，但新项目投稿会等待知识库就绪。不要将真实密钥提交到仓库。

`docker-compose.yml` 已给 Web 和 Worker 接入上述环境变量。周期监测复用 `geo-review-worker`，需保持该服务运行；人工触发监测不依赖 Worker。本文未对现有部署执行变更。

数据库沿用仓库的 `ensure_schema` 增量建表和补列方式。旧投稿的 `project_id` 为空，继续走原有流程；新增项目稿件使用更严格的审批和发布验收流程。原图未修改。

## 明确的实施边界

- 首版审批为固定的串行节点，尚无门户用户目录选择、会签、审批转交或超时消息推送。审批人和项目范围建立后固定，避免在途稿件规则变化。
- 临时入口使用现有持有邀请链接的会话机制，尚未追加手机或邮箱验证码。邀请可续用至到期；失效后由负责人重新邀请。
- 发布验收先采用人工核对。尚未接入渠道正文抓取、阅读互动量接口或附件形式的截图凭证；目前支持凭证说明和链接。
- 新项目一篇稿件对应一条发布记录；多渠道分别投稿审批与验收，尚无单篇稿件多渠道独立验收界面。
- 监测基于持续导入的 GEO 批次，不自动发起付费模型采集或互联网爬取。目标问题作为项目要求记录，采样问题集仍由“我的分析”配置。观测数据是累计引用，趋势变化不代表因果归因；不同批次的采样口径仍须人工保持一致。
- 固定 KB 判据接口当前只提供 agency 可见的标准、禁用和风险条目，正文上限 20000 字。不能把此包理解为所有产品知识均已审核；未覆盖的事实交给人工核实。

## 验证

测试使用临时数据库、模拟 KB 和模型响应，覆盖现有投稿回归、新流程端到端、权限隔离、审批并发、换版重审、发布补正与旧请求失效、KB 失败和摘要校验、统计数据隔离及周期调度。前端通过生产构建；真实登录、真实 KB/模型与外部发布渠道尚待联调。
